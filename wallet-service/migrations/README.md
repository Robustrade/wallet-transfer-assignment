# Database migrations

PostgreSQL migrations are applied and verified by the integration tests.
See the [service README](../README.md) for setup, migration, and seed commands.

- `000001_create_wallets.up.sql` creates `wallets`, `transfers`, `ledger_entries`,
  and `idempotency_records`, followed by supporting indexes, in the same file.
- `000001_create_wallets.down.sql` removes `idempotency_records`, `ledger_entries`,
  `transfers`, and `wallets` in that order. Dropping the tables also removes their
  indexes and the ledger identity sequence. Rollback deletes the data and does
  not cascade to unrelated database objects.

golang-migrate tracks versions and dirty failures in `schema_migrations`.
Its default PostgreSQL mode sends each file as one query, which PostgreSQL executes
atomically. Keep `x-multi-statement` disabled. Tests verify rollback on migration
failure and up/down/up execution; no migration runs automatically at API startup.

## Wallet storage contract

- `id` is an application-supplied string, supporting IDs such as `wallet_1`.
- `currency_code` is required and has three uppercase ASCII letters. This checks
  the code's format only; the application must validate supported currencies and
  their minor-unit scales. Currency metadata is outside this migration's scope.
- `balance_minor` is an exact integer balance in the wallet's currency, defaults
  to zero, and cannot be negative. For example, INR 100.00 is stored as `10000`,
  JPY 100 as `100`, and KWD 100.000 as `100000`.
- `created_at` records an absolute instant, with the inserting transaction's
  timestamp as its default.
- `UNIQUE (id, currency_code)` supports references to a wallet and its currency
  together. It does not prevent multiple wallets from sharing a currency.

The transfer implementation must keep a funded wallet's currency fixed and update
balances inside a transaction with appropriate row locks. The nonnegative balance
constraint alone does not provide the complete transfer or concurrency guarantees.

## Transfer storage contract

- `id` is a UUID generated by PostgreSQL when omitted.
- `from_wallet_id` and `to_wallet_id` reference existing, different wallets.
  A referenced wallet cannot be deleted or have its ID or currency changed.
- `currency_code` is required. Both foreign keys reference `(id, currency_code)`
  in `wallets`, enforcing that the source wallet, destination wallet, and transfer
  all use the same currency. Application validation can provide a readable error
  before a database constraint rejects a mismatched request.
- `amount_minor` is a positive integer in the transfer's currency.
- `status` defaults to `PENDING`. Pending transfers have neither a completion
  timestamp nor a failure code. `PROCESSED` requires a completion timestamp and
  no failure code; `FAILED` requires both a completion timestamp and a failure
  code, such as `INSUFFICIENT_FUNDS`.
- `created_at` defaults to the transaction start time; `completed_at` is supplied
  by the application when it records a final outcome.

The checks validate allowed row values, not historical state transitions.
The transfer implementation must guard updates so only pending transfers reach
a final state, and commit the balances, ledger entries, and outcome together.
Missing-wallet and currency-mismatch requests must be rejected before creating a
transfer row.

## Ledger storage contract

- `id` is a database-generated `BIGINT` identity, separate from the transfer UUID.
- `transfer_id` and `wallet_id` reference existing transfers and wallets. Those
  referenced rows cannot be deleted while ledger entries reference them.
- `entry_type` is `DEBIT` or `CREDIT`, and `amount_minor` is a positive integer.
  A transfer of INR 100 writes a debit of `10000` for the source and a credit of
  `10000` for the destination, linked to the same transfer ID.
- `UNIQUE (transfer_id, entry_type)` permits at most one entry of each type for
  a transfer. It does not guarantee that both entries exist or balance.

The transfer implementation must write exactly two equal entries for a successful
transfer, using the source wallet for the debit and the destination for the
credit. Amounts must equal the transfer amount in its currency. Failed transfers
must have no ledger entries. Commit the entries, balance changes, and transfer
outcome together. Treat committed entries as permanent history; this schema does
not independently forbid updates or deletion of ledger entries.

## Idempotency storage contract

- `idempotency_key` is a globally unique, client-supplied string of 1 to 128
  characters. Retries of the same operation must reuse it.
- `request_payload` stores the normalized request fields as `JSONB`. The
  application compares those fields when a key is reused and rejects a different
  payload. JSON object key order and whitespace do not affect the stored meaning.
- `transfer_id` optionally links a single record to a transfer. It may be null
  for a saved rejection with no transfer; several such records are allowed.
- `http_status` stores the response code from 200 to 599. `response_body` stores
  the serialized JSON as `TEXT` to preserve the body returned to the client.
- Both response fields start null while the transaction claims the key, then
  must be filled before committing. The check prevents only one field being
  populated; it does not itself prevent committing two null response fields.

Claim keys through the primary key's uniqueness constraint. Store the response
in the same transaction as the transfer, balance changes, and ledger entries.
Persist replayable business failures according to the API contract; roll back
transient database failures so the request can be retried. The transfer service
implements this claim/save/replay flow. Retain records for the assignment so
retries remain safe.

## Indexes

- Transfers have indexes on `(from_wallet_id, created_at DESC)` and
  `(to_wallet_id, created_at DESC)` for wallet history lookups and foreign-key
  reference checks.
- Ledger entries have an index on `(wallet_id, created_at DESC, id DESC)` for
  wallet history with a stable ordering when timestamps match.
- Primary keys and unique constraints already provide indexes for key lookups,
  transfer ledger lookups, and idempotency transfer references. No duplicate
  indexes or JSON payload index are needed for those access patterns.

## Verification

`make test` verifies migrations, constraints, seed preservation, guarded states,
balanced ledger writes, saved-result replay, rollback, concurrent key claims,
wallet lock ordering, and cancellation against isolated PostgreSQL databases.
Service tests also verify atomic transfers and prevent concurrent double spending.
