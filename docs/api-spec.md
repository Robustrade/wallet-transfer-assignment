# Wallet Transfer Service — API Spec

## 1. Overview

The API exposes a single endpoint, `POST /transfers`, which moves an amount
from one wallet to another. The requirements behind it are in
[requirements.md](requirements.md).

Conventions:

- Request and response bodies are JSON. The `Content-Type` header is not
  checked; a body that is not a single JSON object is rejected with an error
  (§4).
- Field names are camelCase, as in the assignment's example request.
- There is no authentication (requirements D-18).
- The path has no version prefix; the endpoint is `/transfers`, as given in
  the assignment.

## 2. Request

`POST /transfers`

```json
{
  "idempotencyKey": "abc123",
  "fromWalletId": "wallet_1",
  "toWalletId": "wallet_2",
  "amount": 100
}
```

| Field            | Type    | Required | Rules |
|------------------|---------|----------|-------|
| `idempotencyKey` | string  | yes      | 1–255 characters |
| `fromWalletId`   | string  | yes      | 1–255 characters; an existing wallet; differs from `toWalletId` |
| `toWalletId`     | string  | yes      | 1–255 characters; an existing wallet |
| `amount`         | integer | yes      | a JSON integer from 1 to 9,223,372,036,854,775,807 (int64 max), in the smallest currency unit |

- `amount` must be written as a JSON integer: `"100"`, `100.5`, and `100.0`
  are rejected.
- Fields not listed above are rejected.
- String fields must not contain the NUL character (U+0000).
- The body is at most 64 KiB (65,536 bytes).

A request that breaks any rule is rejected with an error (§4), and nothing is
stored.

## 3. Responses

A request that passes validation either creates a transfer or replays an
earlier one, and the response returns that transfer.

| Outcome                                | Status                     | Body              |
|----------------------------------------|----------------------------|-------------------|
| Transfer `PROCESSED`                   | `201 Created`              | Transfer          |
| Transfer `FAILED` (insufficient funds) | `422 Unprocessable Entity` | Transfer          |
| Replay of an earlier request           | the original status        | the original body |
| Rejected request                       | see §4                     | Error             |

Transfer body:

| Field           | Type   | Description |
|-----------------|--------|-------------|
| `transferId`    | string | UUIDv7 generated by the service |
| `state`         | string | `PROCESSED` or `FAILED` |

`201 Created`

```json
{
  "transferId": "0192f3a4-5b6c-7d8e-9f01-23456789abcd",
  "state": "PROCESSED"
}
```

`422 Unprocessable Entity`

```json
{
  "transferId": "0192f3a4-6c7d-7e8f-a012-3456789abcde",
  "state": "FAILED"
}
```

## 4. Errors

A `4xx` response stores nothing; for a `500`, see §6. Every error response
has this body:

```json
{
  "error": {
    "code": "SAME_WALLET",
    "message": "fromWalletId and toWalletId must differ"
  }
}
```

- `code` identifies the case and is stable; clients branch on it.
- `message` is human-readable text for debugging; clients should not parse it.
- When a request breaks several rules, only the first one is reported,
  following the order of checks in §6.

| Case                                                           | Status                      | Code                     |
|----------------------------------------------------------------|-----------------------------|--------------------------|
| Body is larger than 64 KiB                                     | `413 Content Too Large`     | `REQUEST_TOO_LARGE`      |
| Body is not a single JSON object (invalid JSON, empty, not an object, or followed by trailing data) | `400 Bad Request` | `INVALID_JSON` |
| Body contains a field not listed in §2                         | `400 Bad Request`           | `UNKNOWN_FIELD`          |
| A field is missing, `null`, empty, not a string where a string is expected, longer than 255 characters, or contains U+0000 | `400 Bad Request` | `INVALID_FIELD` |
| `amount` is present but not a JSON integer from 1 to int64 max | `400 Bad Request`           | `INVALID_AMOUNT`         |
| `fromWalletId` equals `toWalletId`                             | `400 Bad Request`           | `SAME_WALLET`            |
| A wallet does not exist                                        | `400 Bad Request`           | `WALLET_NOT_FOUND`       |
| `idempotencyKey` was already used with a different body        | `409 Conflict`              | `IDEMPOTENCY_KEY_REUSED` |
| Unexpected server error (for example, database unavailable)    | `500 Internal Server Error` | `INTERNAL_ERROR`         |

## 5. Idempotency

Every request carries an `idempotencyKey` (§2). Keys are global across the
service and are kept indefinitely.

| Situation                                        | Result |
|--------------------------------------------------|--------|
| New key                                          | The request is processed, and its result is stored with the key |
| Same key, same body                              | Replay: the original status and body are returned (§3); no new transfer, no side effects |
| Same key, different body                         | `409 IDEMPOTENCY_KEY_REUSED`; the original transfer is unaffected |
| Same key while the first request is in progress  | The second request waits for the first to finish, then returns its result |

- **Same body** means the same `fromWalletId`, `toWalletId`, and `amount`,
  compared by value: whitespace and field order in the JSON don't matter.
- Replaying the key of a `FAILED` transfer returns the same `422` response,
  even if the source wallet's balance has grown since.
- Only stored transfers (`PROCESSED` or `FAILED`) use up a key. A `4xx`
  response (§4) stores nothing, so its key can be sent again.
- If the in-progress request fails before it commits, it stores nothing, and
  the waiting request is processed as a new request.
- After a `500`, retrying with the same key is safe: it replays the transfer
  if one was stored (§6), and runs as a new request if not.
- Keys are stored durably, so a replay returns the original result after a
  restart, or when the client never received the first response.

## 6. Processing Rules

### Order of Checks

Checks run in this order, and the first one that fails decides the response.

1. The body is at most 64 KiB → otherwise `REQUEST_TOO_LARGE`; it is a single
   JSON object → otherwise `INVALID_JSON`
2. The body has no fields beyond those in §2 → otherwise `UNKNOWN_FIELD`
3. `idempotencyKey`, `fromWalletId`, `toWalletId`, and `amount` are present
   and not `null`, and the three string fields are JSON strings of 1–255
   characters with no U+0000, checked in that order → otherwise
   `INVALID_FIELD`
4. `amount` is a JSON integer from 1 to int64 max → otherwise `INVALID_AMOUNT`
5. `fromWalletId` differs from `toWalletId` → otherwise `SAME_WALLET`
6. The `idempotencyKey` is new → if it exists with the same body, replay
   (§5); with a different body, `IDEMPOTENCY_KEY_REUSED`
7. Both wallets exist → otherwise `WALLET_NOT_FOUND`
8. The source balance is at least `amount` → `PROCESSED` (`201`); otherwise
   `FAILED` (`422`)

Steps 1–5 check only the request. Steps 6–8 run inside the transfer's
database transaction.

### Balance Rule

- A transfer is `PROCESSED` when the source balance is greater than or equal
  to `amount`. The source balance decreases by `amount`, and the destination
  balance increases by `amount`.
- Otherwise the transfer is `FAILED`, and no balance changes.
- A balance can reach zero but never go below it.

### States

- A transfer is created as `PENDING` and moves to `PROCESSED` or `FAILED`
  within the same database transaction. Clients only ever see `PROCESSED` or
  `FAILED`.
- `PROCESSED` and `FAILED` are final.

### Atomicity and Concurrency

- Each transfer is committed in one database transaction, or not at all. That
  covers its idempotency record, the transfer, both balance changes, and both
  ledger entries.
- If anything fails before commit, nothing is stored, and the response is
  `500 INTERNAL_ERROR`.
- If the connection fails during the commit, the service cannot tell whether
  the commit succeeded, and the response is also `500 INTERNAL_ERROR`. Either
  everything was stored or nothing was; a retry with the same key finds out
  safely (§5).
- Concurrent requests behave as if they ran one after another: each balance
  check sees every transfer committed before it, so two transfers can never
  spend the same funds.

## 7. Side Effects

| Outcome                | Transfer stored  | Ledger entries | Balances                                    | Idempotency key stored          |
|------------------------|------------------|----------------|---------------------------------------------|---------------------------------|
| `201` `PROCESSED`      | yes, `PROCESSED` | 2              | source − `amount`, destination + `amount`   | yes, with the result to replay  |
| `422` `FAILED`         | yes, `FAILED`    | none           | unchanged                                   | yes, with the result to replay  |
| Replay                 | no new transfer  | no new entries | unchanged                                   | no change                       |
| `400` / `409` / `413` rejected | no               | none           | unchanged                                   | no                              |
| `500` server error¹    | no               | none           | unchanged                                   | no                              |

¹ Unless the commit's outcome is unknown (§6): then everything in the `201`
or `422` row may have been stored.

The two ledger entries of a `PROCESSED` transfer:

| wallet_id      | transfer_id  | type     | amount   |
|----------------|--------------|----------|----------|
| `fromWalletId` | `transferId` | `DEBIT`  | `amount` |
| `toWalletId`   | `transferId` | `CREDIT` | `amount` |

Every request, whatever its outcome, logs that outcome (requirements NFR-5).
