# Wallet Transfer Service — Database Design

**Status:** Implemented (aligned with `migrations/`)  
**Database:** PostgreSQL  
**Access:** GORM with explicit transactions and selected SQL statements  
**Schema management:** golang-migrate (`make migrate-up`)  
**Related documents:** `ASSIGNMENT.md`, `docs/REQUIREMENTS.md`, `docs/ARCHITECTURE.md`, `docs/API.md`

## 1. Purpose and requirements

This document defines the persistent model and consistency rules for wallet-to-wallet transfers. The assignment requires atomic balance changes, exactly two balanced ledger entries per successful transfer, protection against concurrent double spending, idempotent request processing, and `PENDING → PROCESSED / FAILED` state transitions.

**Project decisions (not imposed by the client):** PostgreSQL, Go/Fiber v3, GORM, golang-migrate, integer minor-unit amounts, synchronous processing within one PostgreSQL transaction, and an idempotency key required by the API contract.

## 2. Data model

```text
wallets (1) ──< transfers.from_wallet_id
wallets (1) ──< transfers.to_wallet_id
transfers (1) ──< ledger_entries (exactly 2 for PROCESSED)
transfers (1) ─── idempotency_records (1 per committed request)
wallets (1) ──< ledger_entries
```

### 2.1 `wallets`

| Column | Type | Rule |
|---|---|---|
| `id` | `BIGINT IDENTITY` | Primary key; wallet identifier |
| `balance` | `BIGINT` | Defaults to `0`; `CHECK (balance >= 0)`; integer minor units |
| `created_at`, `updated_at` | `TIMESTAMPTZ` | Default to current time |

Wallet balances are a materialized current balance. Ledger entries provide the audit trail for transfer movements. This design assumes a **single currency/denomination**; multi-currency transfers are not defined. There is no `is_active` flag: all existing wallets can transact.

### 2.2 `transfers`

| Column | Type | Rule |
|---|---|---|
| `id` | `BIGINT IDENTITY` | Primary key; generated by the database |
| `idempotency_key` | `VARCHAR(255)` | Required, unique |
| `from_wallet_id` | `BIGINT` | FK to `wallets.id` |
| `to_wallet_id` | `BIGINT` | FK to `wallets.id`; `CHECK (from_wallet_id <> to_wallet_id)` |
| `amount` | `BIGINT` | `CHECK (amount > 0)` |
| `status` | `VARCHAR(20)` | `PENDING` (default), `PROCESSED`, `FAILED`; enforced by `chk_transfer_status` |
| `failure_reason` | `TEXT` | Set for `FAILED` (for example `INSUFFICIENT_FUNDS`), otherwise `NULL` |
| `created_at`, `updated_at` | `TIMESTAMPTZ` | Audit timestamps |

The request fingerprint lives on `idempotency_records`, not on `transfers`. A committed `FAILED` transfer represents a deterministic business rejection, such as insufficient funds. Infrastructure failures are rolled back, not recorded as terminal `FAILED` transfers.

### 2.3 `ledger_entries`

| Column | Type | Rule |
|---|---|---|
| `id` | `BIGINT IDENTITY` | Primary key |
| `transfer_id` | `BIGINT` | FK to `transfers.id` |
| `wallet_id` | `BIGINT` | FK to `wallets.id` |
| `entry_type` | `VARCHAR(10)` | `DEBIT` or `CREDIT` (`chk_ledger_entry_type`) |
| `amount` | `BIGINT` | `CHECK (amount > 0)` |
| `created_at` | `TIMESTAMPTZ` | Defaults to current time |

`UNIQUE (transfer_id, entry_type)` allows at most one debit and one credit per transfer. One successful transfer creates exactly one `DEBIT` for its source and one `CREDIT` for its destination, each equal to `transfers.amount`. A failed transfer creates **zero** ledger entries. Ledger rows must not be modified after commit.

### 2.4 `idempotency_records`

| Column | Type | Rule |
|---|---|---|
| `id` | `BIGINT IDENTITY` | Primary key |
| `idempotency_key` | `VARCHAR(64)` | Unique; `CHECK (LENGTH(idempotency_key) BETWEEN 8 AND 64)` |
| `request_hash` | `VARCHAR(64)` | SHA-256 hex of the canonical business request |
| `transfer_id` | `BIGINT` | Nullable FK to `transfers.id`; set when the response is saved |
| `response_status` | `INT` | Original terminal HTTP status; `CHECK BETWEEN 100 AND 599` |
| `response_body` | `JSONB` | Original terminal response payload |
| `created_at`, `updated_at` | `TIMESTAMPTZ` | Default to current time |

`chk_response_complete` requires `response_status` and `response_body` to be both `NULL` or both set. A row without a response means the key is claimed but its transaction has not finished; it is never visible to other transactions after commit in normal operation.

Idempotency records are inserted in the **same transaction** as the terminal transfer outcome. This design keeps records indefinitely unless a separately documented retention policy is adopted. Do not purge keys casually: reuse after deletion can cause duplicate transfers.

`response_body` is `JSONB`, so PostgreSQL re-formats it on read (adds spaces). The service re-serialises it to the canonical compact form before replaying it, which keeps replays byte-identical to the original response.

## 3. SQL migrations

Files live in `migrations/` and are applied in order with `make migrate-up` (`make migrate-down` rolls back one step):

| Version | Creates |
|---|---|
| `000001_create_wallets` | `wallets` |
| `000002_create_transfers` | `transfers`, `idx_transfers_from_wallet`, `idx_transfers_to_wallet` |
| `000003_create_ledger_entries` | `ledger_entries`, `idx_ledger_wallet_id` |
| `000004_create_idempotency_records` | `idempotency_records` |

Abridged definitions (see the files for the complete SQL):

```sql
CREATE TABLE wallets (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    balance BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT chk_wallet_balance CHECK (balance >= 0)
);

CREATE TABLE transfers (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    idempotency_key VARCHAR(255) NOT NULL UNIQUE,
    from_wallet_id BIGINT NOT NULL REFERENCES wallets(id),
    to_wallet_id BIGINT NOT NULL REFERENCES wallets(id),
    amount BIGINT NOT NULL CHECK (amount > 0),
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    failure_reason TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT chk_different_wallets CHECK (from_wallet_id <> to_wallet_id),
    CONSTRAINT chk_transfer_status CHECK (status IN ('PENDING', 'PROCESSED', 'FAILED'))
);

CREATE TABLE ledger_entries (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    transfer_id BIGINT NOT NULL REFERENCES transfers(id),
    wallet_id BIGINT NOT NULL REFERENCES wallets(id),
    entry_type VARCHAR(10) NOT NULL,
    amount BIGINT NOT NULL CHECK (amount > 0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT chk_ledger_entry_type CHECK (entry_type IN ('DEBIT', 'CREDIT')),
    CONSTRAINT uq_ledger_transfer_entry_type UNIQUE (transfer_id, entry_type)
);

CREATE TABLE idempotency_records (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    idempotency_key VARCHAR(64) NOT NULL,
    request_hash VARCHAR(64) NOT NULL,
    transfer_id BIGINT REFERENCES transfers(id),
    response_status INT,
    response_body JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_idempotency_key UNIQUE (idempotency_key),
    CONSTRAINT chk_idempotency_key_length CHECK (LENGTH(idempotency_key) BETWEEN 8 AND 64),
    CONSTRAINT chk_response_status CHECK (response_status BETWEEN 100 AND 599),
    CONSTRAINT chk_response_complete CHECK (
        (response_status IS NULL AND response_body IS NULL)
        OR (response_status IS NOT NULL AND response_body IS NOT NULL))
);

CREATE INDEX idx_transfers_from_wallet ON transfers(from_wallet_id);
CREATE INDEX idx_transfers_to_wallet ON transfers(to_wallet_id);
CREATE INDEX idx_ledger_wallet_id ON ledger_entries(wallet_id);
```

Each migration has a matching `.down.sql` that drops its table. Destructive `down` migrations are for controlled development/testing only; never run them against valuable data without an explicit rollback plan.

## 4. Transaction boundary and state management

`POST /transfers` is processed synchronously inside **one database transaction**:

1. Validate the request before opening a transaction; calculate a deterministic request fingerprint.
2. Begin transaction (`READ COMMITTED`, the PostgreSQL default).
3. Claim the key: `INSERT INTO idempotency_records (idempotency_key, request_hash) … ON CONFLICT (idempotency_key) DO NOTHING`.
4. If no row was inserted, read the existing record. Different hash → HTTP `409`. Same hash with a stored response → replay it. Same hash without a stored response → `409` "still in progress". Do not touch balances.
5. If the claim won, lock the source and destination wallet rows **one at a time in ascending wallet ID order**, with `SELECT … FOR UPDATE`. A missing wallet aborts the transaction (`404`) and rolls the claim back.
6. Insert the `PENDING` transfer row (`ON CONFLICT (idempotency_key) DO NOTHING`). This happens **after** the wallet locks: the foreign keys take `FOR KEY SHARE` locks on both wallets, and doing it first makes concurrent transfers deadlock when they upgrade to `FOR UPDATE`.
7. Check sufficient balance **under lock**.
8. On deterministic business rejection: mark `FAILED` with `failure_reason`, save the original response on the idempotency record, and **commit**. Do not update balances or create ledger entries.
9. On success: debit source, credit destination (checking `BIGINT` overflow first), insert debit and credit ledger rows, mark `PROCESSED`, save the original HTTP status/body, and **commit**.
10. Return the recorded result after successful commit.

A crash or database error **before commit** rolls back all writes. A crash **after commit** leaves the complete result, recoverable by retrying with the same key. `PENDING` is ordinarily uncommitted and not visible to other transactions in this synchronous design; no recovery worker is required to process persisted pending rows.

## 5. Concurrency and isolation

- `READ COMMITTED` plus explicit row locks and uniqueness constraints is the baseline.
- Always lock both wallet rows in a deterministic order, regardless of transfer direction. This reduces deadlock risk; it does not eliminate all possible deadlocks.
- The second concurrent debit waits for the first, then checks the updated balance. Never validate balance only before acquiring the lock.
- The unique constraint on `idempotency_records.idempotency_key` arbitrates concurrent requests with the same key; the claim is an atomic insert rather than read-then-insert.
- For SQLSTATE `40P01` (deadlock) or `40001` (serialization failure), retry the **entire** transaction (3 attempts, 100 ms then 200 ms backoff), retaining the same idempotency key.
- For uncertain COMMIT outcomes, do not assume rollback. Resolve by reading the key on a new connection; if still unknown, return a retryable/unknown-outcome response and instruct the client to retry with the same key.
- Keep transactions short and free of network calls.

## 6. Database invariants and limitations

**Required invariants:**

- Wallet balance never becomes negative.
- Successful transfers debit and credit the same amount atomically.
- Exactly two ledger entries are inserted per successful transfer: source debit and destination credit.
- Failed transfers do not alter balances and have no ledger entries.
- The same idempotency key cannot produce multiple committed transfers.
- Terminal transfer statuses cannot be transitioned again by application logic.

**What the proposed constraints guarantee:**

- `CHECK (balance >= 0)` prevents negative committed wallet balances.
- `UNIQUE (idempotency_key)` on both `idempotency_records` and `transfers` prevents duplicate claims.
- `UNIQUE (transfer_id, entry_type)` prevents multiple debit or multiple credit rows for one transfer.
- Foreign keys prevent orphan references.

**What they do not guarantee by themselves:** The schema does **not** independently guarantee that a `PROCESSED` transfer has both ledger entries, that entries reference the correct source/destination, or that ledger amounts match the transfer. These are enforced by the transaction service and integration tests. Stronger DB-only enforcement would require deferred constraint triggers or tightly restricted write privileges. Ledger immutability also needs write-permission restrictions or triggers if direct SQL writers are in scope. These tradeoffs are recorded in `docs/DECISIONS.md`.

Amount arithmetic must be checked for `BIGINT` overflow before updating balances. Currency, initial wallet funding, wallet creation, and cross-currency behavior require explicit policy before expansion.

## 7. GORM and migration responsibilities

- **golang-migrate** owns all schema creation/alteration; do **not** call `AutoMigrate` at startup.
- **GORM** owns application persistence and transaction execution. Use `db.Transaction(...)` or explicit `Begin/Commit/Rollback` with errors checked.
- Pass the **same transaction handle** through every repository operation in a transfer.
- Use GORM row-locking clauses or carefully parameterized raw SQL for `FOR UPDATE` and `INSERT ... ON CONFLICT ... RETURNING`.
- Keep database types/constraints consistent with domain and API validation.
- Use SQL migration files with sequential version numbers; do not edit already-applied migrations in shared environments.

## 8. Running locally

### With Docker (recommended)

```bash
make docker-up      # docker compose up -d --build --wait
make docker-reset   # wipe the volume and start from a fresh database
```

Compose starts PostgreSQL (creating `DB_NAME` on first start), waits for its health check, runs the `migrate` job, runs the `seed` job (100 wallets with random balances, only if `wallets` is empty), and then starts the API on `http://localhost:8090`. A failed migration or seed prevents the API from starting. PostgreSQL is also published on host port `5433`; data lives in the `pgdata` volume.

### Without Docker

Run PostgreSQL yourself, configure `.env` (see `.env.example`), then:

```bash
make migrate-up         # apply migrations with golang-migrate
go run ./cmd/api        # start the API
make test               # unit tests, no database needed
make test-integration   # PostgreSQL integration and concurrency tests
```

Notes:

- The integration tests use the database from `.env`. They create their own wallets and never modify existing rows, so a shared development database is safe; use a dedicated database for stricter isolation.
- Keep credentials in environment configuration and never commit real secrets.
- A nonzero `migrate` exit status must be treated as a failed deployment (in Compose it blocks the API automatically).

## 9. Test and verification plan

Automated coverage is described in `docs/TESTING.md`. In short:

1. Migrations apply on a clean PostgreSQL instance (`make migrate-up`).
2. Schema constraints are exercised by the integration tests (negative balance, duplicate ledger entry type).
3. Successful transfer updates both balances and writes exactly two correct ledger entries.
4. Insufficient funds commits a `FAILED` transfer with zero ledger entries and unchanged balances.
5. Same key/same payload replays the stored result (byte-identical); same key/different payload conflicts.
6. Concurrent transfers cannot overdraw the same wallet.
7. Opposite-direction concurrent transfers complete without deadlock.
8. Injected failure before commit leaves no partial updates.
9. Retry after a committed transfer does not execute it again.
10. Deadlocks and serialization failures are retried, not reported as business failures.

## 10. Decisions and open items

Decided:

- Wallet-not-found: `404`, no committed transfer, key not reserved (see `docs/API.md`).
- Wallet and transfer IDs are database identity `BIGINT` values.

Open:

- Initial wallet funding/seed strategy for demonstration data.
- Whether to add database triggers for ledger immutability and cross-row integrity.
- Whether idempotency keys need tenant/user scoping if authentication is later introduced.
- Currency denomination and any future multi-currency support.
