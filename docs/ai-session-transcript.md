## 1. Proposed architecture

**Stack:** Go 1.24, `net/http` with the Go 1.22+ `ServeMux` patterns (no framework), `pgx/v5` with `pgxpool`, `golang-migrate` or plain embedded SQL migrations, `testify`. Money is `int64` in minor units (no floats).

```
cmd/server/main.go            wiring, config, graceful shutdown
internal/domain/              Wallet, Transfer, LedgerEntry, states, sentinel errors, validation (pure, no I/O)
internal/service/             TransferService: idempotency + workflow + tx orchestration
internal/repository/          interfaces (TxManager, WalletRepo, TransferRepo, LedgerRepo, IdempotencyRepo)

migrations/                   SQL schema

```

- **Handler:** decodes JSON, reads the `Idempotency-Key` header or body field, maps errors to HTTP codes. No business logic.
- **Service:** owns the transaction boundary through a `TxManager.WithinTx(ctx, fn)` interface. The workflow decisions (replay or not, enough funds, state changes) live here.
- **Repository:** persistence only. Methods take the tx from context. The repo never decides workflow.
- **Domain:** `Transfer.MarkProcessed()` and `MarkFailed()` enforce the state machine. `NewTransfer` validates the amount and rejects self-transfers.

## 2. Database schema (PostgreSQL)

```sql
wallets(
  id TEXT PK,
  balance BIGINT NOT NULL CHECK (balance >= 0),   -- DB enforces no overdraft
  version BIGINT NOT NULL DEFAULT 0,              -- optional, for audit only
  created_at, updated_at)

transfers(
  id UUID PK,
  idempotency_key TEXT NOT NULL UNIQUE,
  from_wallet_id TEXT NOT NULL REFERENCES wallets,
  to_wallet_id   TEXT NOT NULL REFERENCES wallets,
  amount BIGINT NOT NULL CHECK (amount > 0),
  status TEXT NOT NULL CHECK (status IN ('PENDING','PROCESSED','FAILED')),
  failure_reason TEXT NULL,
  created_at, updated_at,
  CHECK (from_wallet_id <> to_wallet_id))

ledger_entries(
  id BIGSERIAL PK,
  transfer_id UUID NOT NULL REFERENCES transfers,
  wallet_id TEXT NOT NULL REFERENCES wallets,
  type TEXT NOT NULL CHECK (type IN ('DEBIT','CREDIT')),
  amount BIGINT NOT NULL CHECK (amount > 0),
  created_at,
  UNIQUE (transfer_id, type))                      -- at most 1 debit + 1 credit per transfer

idempotency_records(
  key TEXT PK,
  request_hash TEXT NOT NULL,                      -- sha256 of canonical request
  transfer_id UUID NULL REFERENCES transfers,
  response_status INT, response_body JSONB,        -- stored original result
  created_at)
```

- **Indexes:** `ledger_entries(wallet_id, id)` for history and reconciliation, `ledger_entries(transfer_id)`, and `transfers(from_wallet_id, created_at)`. The unique constraints give us the idempotency indexes.
- **Ledger immutability:** a trigger or revoked `UPDATE`/`DELETE` makes the ledger append-only.
- **Optional hardening:** a deferred constraint trigger that checks `SUM(DEBIT) = SUM(CREDIT)` per transfer. That is a strong answer to the rubric question "can ledger rows exist without a transfer?" The foreign key already prevents it.

**Balance design: stored balance plus ledger, and they must reconcile.**
- A stored balance gives O(1) reads and a natural place for the `CHECK (balance >= 0)` guard. Deriving from the ledger would need a `SUM` under lock on every transfer.
- The ledger is the audit source of truth. A test and a reconciliation query assert `wallet.balance == initial + SUM(credits) − SUM(debits)`.

## 3. Transfer flow and concurrency

All inside **one DB transaction** at `READ COMMITTED`. The row locks, not a higher isolation level, give us correctness.

1. Validate input (amount > 0, wallets differ, key non-empty) before touching the DB.
2. **Claim the idempotency key:**
   `INSERT INTO idempotency_records(key, request_hash) … ON CONFLICT (key) DO NOTHING`
   - **Conflict, hash differs:** return `422` (key reused with a different payload).
   - **Conflict, hash same:** replay the stored response. The unique index makes a concurrent duplicate **block until the first transaction commits or rolls back**, so it either sees the stored result or takes over cleanly.
   - **Inserted:** we own the key, so continue.
3. Insert the transfer as `PENDING`.
4. **Lock both wallet rows in a deterministic order:** `SELECT … FROM wallets WHERE id = ANY($1) ORDER BY id FOR UPDATE`. Always locking the lower ID first means A→B and B→A cannot deadlock.
5. If a wallet is missing → `FAILED(WALLET_NOT_FOUND)`. If `balance < amount` → `FAILED(INSUFFICIENT_FUNDS)`.
6. On success:
   - `UPDATE wallets SET balance = balance − $amt` on the source, and `+ $amt` on the destination.
   - Insert both ledger rows.
   - `PENDING → PROCESSED`, using a guarded `UPDATE … WHERE status='PENDING'` so duplicates and retries can never move a state twice.
7. Store the response in `idempotency_records` and **commit**. Everything is atomic: the key, the transfer, the ledger and the balances commit together or not at all.

**Business failures are recorded, not rolled back.**
- An insufficient-funds failure commits the `FAILED` transfer and the stored response, with no ledger entries and no balance change.
- A retry then gets the **same** `422`.
- This is deliberate exactly-once semantics: a failed attempt under a key is a final result. To retry, use a new key.
- Infrastructure errors (timeouts, deadlocks, serialization failures) roll back everything including the key claim, so a retry is a clean first attempt.

**Why this design (for L2):**
- `CHECK (balance >= 0)` is the last line of defense. Even if app logic had a bug, Postgres refuses to overdraft.
- Pessimistic locking suits wallets because contention on a hot wallet is real and retry storms are costly. Optimistic locking would retry-loop under a hot account.
- The "first request committed but the response was lost" scenario works because the key and the result commit atomically with the money movement.

## 4. Edge cases to handle explicitly

| Case | Handling |
|---|---|
| Duplicate sequential request | Replay the stored response. Same status and body, plus an `Idempotent-Replayed: true` header. |
| Duplicate concurrent requests (same key) | The unique-index conflict blocks the second one. It replays the result once the first commits. |
| Same key, different payload | `422 IDEMPOTENCY_KEY_REUSED`, based on the request hash. |
| Two debits on one wallet | Serialized by `FOR UPDATE`. One succeeds and one fails with insufficient funds. |
| A→B and B→A simultaneously | Ordered locking, so no deadlock. |
| Self-transfer, zero or negative amount, overflow | Rejected at the domain layer, with `CHECK`s as backup. |
| Unknown wallet | `404`-style failure. Decision: record it as a `FAILED` transfer, or reject before creating one. |
| Crash mid-transaction | Postgres rolls back, so there are no partial writes. |
| Crash after commit, before response | The client retries with the same key and gets the stored result. |
| Stuck `PENDING` | Not possible with the single-transaction design, because `PENDING` never commits on its own. I'll document this. If we ever split into async steps, a reaper is needed. |
| Deadlock or serialization error (`40P01`, `40001`) | Bounded retry with backoff in `WithinTx`. Safe because nothing external has been committed. |
| Request timeouts | `context` is passed through. Cancellation rolls back the transaction. |
| Idempotency key retention | Out of scope. I'll note a TTL and cleanup job as a future item. |
| Key scoping | I'd keep a global key for simplicity. I'll note that a real system scopes it per client or tenant. |
