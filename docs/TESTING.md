# Wallet Transfer Service — Testing Guide

## 1. Purpose and scope

This document describes how to validate the correctness, resilience, and performance of the Go/Fiber v3, GORM, and PostgreSQL wallet transfer service.

**API:** `POST /transfers`

```json
{
  "idempotencyKey": "unique-key-123",
  "fromWalletId": 1,
  "toWalletId": 2,
  "amount": 1000
}
```

Amounts and balances are `int64` **minor currency units**. For INR, `1000` means ₹10.00.

Core invariants:

1. A processed transfer atomically debits the sender, credits the receiver, writes **exactly one DEBIT and one CREDIT** ledger entry, marks the transfer `PROCESSED`, and saves its idempotency response.
2. A transfer rejected for insufficient funds is recorded as `FAILED`, changes neither balance, writes **zero** ledger entries, and saves the original 409 response.
3. No committed wallet balance may be negative.
4. A reused idempotency key with the same payload returns the original HTTP status and body without a second transfer; the same key with different payload returns 409.
5. Opposite-direction transfers and other concurrent operations must not cause lost updates, double debits, or permanent lock waits.
6. On transaction errors, all uncommitted changes roll back. On uncertain COMMIT, the service must reconcile the idempotency record rather than blindly replaying the operation.

## 2. Test environment and prerequisites

- Go version compatible with the project and Fiber v3.
- PostgreSQL (the version used by the project), with migrations applied (`make migrate-up`).
- Node.js 18+ for HTTP concurrency scripts (uses built-in `fetch` and `crypto`).
- A **dedicated test database**; never run stress tests against production wallets.
- API reachable at `http://localhost:$APP_PORT` (`APP_PORT` from `.env`, for example `8009`; adjust the scripts' `API_URL`).
- Known test wallets and recorded opening balances for balance-reconciliation tests.

Example test data: 1,000 wallets with nonnegative random opening balances (IDs are generated by the database):

```sql
INSERT INTO wallets (balance, created_at, updated_at)
SELECT floor(random() * 1000000)::bigint, now(), now()
FROM generate_series(1, 1000);
```

**Do not assume wallet IDs are 1–1000** if the database already contained wallets. For HTTP tests, choose existing IDs. Capture opening balances before the run if you want to prove total balance conservation.

```sql
SELECT id, balance FROM wallets ORDER BY id LIMIT 20;
SELECT count(*) AS wallet_count, sum(balance) AS total_balance FROM wallets;
```

> Random opening balances are seed data, not ledger movements. To reconcile each wallet against its ledger, record its opening balance separately.

### Automated test suite in this repository

| Command | Scope |
| --- | --- |
| `make test` | Unit tests, no database: `domain/`, `handler/` (stub service, status mapping), `service/` (in-memory fake store that enforces FKs, `balance >= 0`, unique keys, guarded status updates and rollback; fault injection for deadlocks, ledger failure and uncertain commit) |
| `make test-integration` | PostgreSQL tests in `internal/feature/wallet/integration/` (build tag `integration`, database from `.env`). Each test creates its own wallets, so existing rows are untouched |

The integration suite covers: persisted transfer, ledger and balances; insufficient funds recorded as `FAILED`; unknown wallet leaving no trace; sequential replay; same key with a different payload; 20 parallel requests with one key (one transfer, identical responses); 20 parallel debits against a balance for 5 (no double spend); 30 parallel transfers on one wallet pair and 40 opposite-direction transfers (deadlock regression); a wallet ring checking money conservation and ledger-versus-balance agreement; schema constraints; and an HTTP end-to-end flow. The manual HTTP race scripts below complement these.

## 4. Unit tests

Keep domain unit tests independent of PostgreSQL.

### 4.1 Wallet debit validation

```go
func TestWalletCanDebit(t *testing.T) {
    tests := []struct {
        name    string
        balance int64
        amount  int64
        wantErr error
    }{
        {"sufficient", 10000, 5000, nil},
        {"exact balance", 10000, 10000, nil},
        {"insufficient", 1000, 2000, domain.ErrInsufficientFunds},
        {"zero amount", 1000, 0, domain.ErrInvalidAmount},
        {"negative amount", 1000, -1, domain.ErrInvalidAmount},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            w := domain.Wallet{ID: 1, Balance: tt.balance}
            err := w.CanDebit(tt.amount)
            if tt.wantErr == nil && err != nil {
                t.Fatalf("unexpected error: %v", err)
            }
            if tt.wantErr != nil && !errors.Is(err, tt.wantErr) {
                t.Fatalf("got %v, want %v", err, tt.wantErr)
            }
        })
    }
}
```

Required imports: `errors`, `testing`, and the project's `internal/domain` package.

### 4.2 Additional domain tests

- `Transfer.Validate`: valid transfer, zero/negative amount, invalid IDs, equal IDs, empty/too-long key.
- `Transfer.ChangeStatus`: only `PENDING → PROCESSED` and `PENDING → FAILED` allowed; terminal states cannot change again.
- `NewLedgerEntries`: two entries, correct wallets, equal positive amounts, opposite entry types.
- `TransferFingerprint`: same input gives same hash; changing sender, receiver, or amount changes hash.
- `IdempotencyRecord.MatchesRequest`: same hash accepted; different hash returns `ErrIdempotencyConflict`.
- Boundary conditions: very large balances, credit overflow prevention, and integer limits.

Run:

```bash
go test ./internal/domain/...
go test ./... -count=1
go test -race ./...
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```

The Go race detector checks **Go memory data races**, not PostgreSQL lost updates or accounting correctness.

## 5. PostgreSQL integration tests

Use a real PostgreSQL instance and isolate test cases. Seed wallets with known balances, run the service operation, then inspect all four tables (`wallets`, `transfers`, `ledger_entries`, `idempotency_records`).

### 5.1 Successful transfer

Given A=10,000 and B=5,000, transfer 2,000 A→B:

- HTTP 201, body includes transfer ID and `PROCESSED`.
- A=8,000, B=7,000.
- Transfer status `PROCESSED`.
- One DEBIT entry for A, one CREDIT entry for B, both amount 2,000.
- Idempotency row contains the same HTTP status and body.

### 5.2 Insufficient funds

Given A=1,000 and B=5,000, transfer 2,000 A→B:

- HTTP 409; transfer status `FAILED`, reason `INSUFFICIENT_FUNDS`.
- A=1,000 and B=5,000.
- No ledger rows for this transfer.
- Repeating the exact request returns the original 409 response.

### 5.3 Missing wallet

Use an ID that does not exist. Expect HTTP 404 and no committed balance or ledger changes. Confirm the failed attempt did not leave a partially committed transfer/idempotency claim.

### 5.4 Transaction rollback (fault injection)

In test-only code, inject a repository failure after the first balance update, after ledger insertion, and before the final status update. Each injected error must cause rollback. Verify both wallet balances and all relevant row counts remain unchanged. **Do not inject faults into production traffic.**

### 5.5 Idempotency replay

For each of a successful transfer and an insufficient-funds transfer, repeat the same key/payload and compare **exact HTTP status and raw response bytes**. Then change the amount while reusing the key: expect 409 and no second transfer.

## 6. Concurrent HTTP tests (Node.js)

The following reusable script supports three patterns:

- `opposite`: alternating A→B and B→A.
- `same-sender`: A→B for all requests.
- `random`: random distinct sender/receiver IDs.

It also supports `same-key` to test concurrent idempotency replay. Requests are started without awaiting previous responses; `Promise.all` waits for all to finish. They are launched **nearly simultaneously**, not guaranteed to arrive in the same microsecond.

The script is committed as [`scripts/concurrency-test.js`](../scripts/concurrency-test.js). It targets the Docker stack by default (`API_URL=http://localhost:8090/transfers`, wallets 1–100 from the seed data); override `API_URL`, `WALLET_A`, `WALLET_B`, `MIN_WALLET_ID`, `MAX_WALLET_ID`, `AMOUNT`, `COUNT`, `MODE` and `TIMEOUT_MS` through environment variables.

Run examples:

```bash
# Start with 10 requests; increase after verifying database state
MODE=opposite COUNT=10 WALLET_A=1 WALLET_B=2 node scripts/concurrency-test.js
MODE=opposite COUNT=100 WALLET_A=1 WALLET_B=2 node scripts/concurrency-test.js
MODE=same-sender COUNT=100 WALLET_A=1 WALLET_B=2 node scripts/concurrency-test.js
MODE=random COUNT=100 MIN_WALLET_ID=1 MAX_WALLET_ID=1000 node scripts/concurrency-test.js
MODE=same-key COUNT=100 WALLET_A=1 WALLET_B=2 node scripts/concurrency-test.js
```

**Interpretation:** A 409 may be a correct business rejection (insufficient funds or idempotency conflict). A timeout or network error does **not** prove the transfer failed; reconcile by idempotency key before retrying.

For `same-key`, expect only one committed transfer and one pair of ledger entries. The completed requests should replay the same HTTP status/body. Verify the database, not only the client summary.

## 7. SQL consistency checks

Run these after tests. A global sum of zero is useful, but **does not alone prove every transfer is correct**.

### 7.1 Overall ledger conservation

```sql
SELECT
  count(*) AS total_entries,
  coalesce(sum(amount) FILTER (WHERE entry_type = 'DEBIT'), 0) AS total_debit,
  coalesce(sum(amount) FILTER (WHERE entry_type = 'CREDIT'), 0) AS total_credit,
  coalesce(sum(CASE
    WHEN entry_type = 'CREDIT' THEN amount
    WHEN entry_type = 'DEBIT' THEN -amount
    ELSE 0 END), 0) AS net_difference
FROM ledger_entries;
```

Expected: `total_debit = total_credit` and `net_difference = 0`.

### 7.2 Strong per-transfer ledger check

Starts from `transfers` to catch missing ledger entries, checks amounts, entry types, and correct wallet ownership. **Expected: zero rows.**

```sql
SELECT
  t.id, t.status, t.amount,
  count(l.id) AS ledger_count,
  coalesce(sum(l.amount) FILTER (WHERE l.entry_type = 'DEBIT'), 0) AS debit,
  coalesce(sum(l.amount) FILTER (WHERE l.entry_type = 'CREDIT'), 0) AS credit
FROM transfers t
LEFT JOIN ledger_entries l ON l.transfer_id = t.id
GROUP BY t.id, t.status, t.amount, t.from_wallet_id, t.to_wallet_id
HAVING
  (t.status = 'PROCESSED' AND NOT (
    count(l.id) = 2
    AND count(l.id) FILTER (
      WHERE l.entry_type = 'DEBIT'
        AND l.wallet_id = t.from_wallet_id
        AND l.amount = t.amount
    ) = 1
    AND count(l.id) FILTER (
      WHERE l.entry_type = 'CREDIT'
        AND l.wallet_id = t.to_wallet_id
        AND l.amount = t.amount
    ) = 1
  ))
  OR (t.status = 'FAILED' AND count(l.id) <> 0)
  OR t.status NOT IN ('PROCESSED', 'FAILED');
```

Note: If an API transaction is actively in progress, its uncommitted `PENDING` row is not visible to a normal separate connection; any **committed** `PENDING` row should be investigated.

### 7.3 Negative wallet balances

```sql
SELECT id, balance FROM wallets WHERE balance < 0;
```

Expected: zero rows. Also keep a DB-level `CHECK (balance >= 0)` constraint.

### 7.4 Duplicate transfer keys

```sql
SELECT idempotency_key, count(*) AS occurrences
FROM transfers
GROUP BY idempotency_key
HAVING count(*) > 1;
```

Expected: zero rows. The unique constraint on `transfers.idempotency_key` is the primary protection.

### 7.5 Idempotency records missing a saved response

```sql
SELECT id, idempotency_key, transfer_id, response_status
FROM idempotency_records
WHERE response_status IS NULL OR response_body IS NULL;
```

Expected: zero rows for committed completed requests.

### 7.6 Successful transfers missing idempotency records

```sql
SELECT t.id, t.idempotency_key, t.status
FROM transfers t
LEFT JOIN idempotency_records i
  ON i.idempotency_key = t.idempotency_key
WHERE i.id IS NULL
   OR i.transfer_id IS DISTINCT FROM t.id
   OR i.response_status IS NULL
   OR i.response_body IS NULL;
```

Expected: zero rows.

### 7.7 Combined wallet balance conservation

For a closed system of internal transfers, the total balance across **all wallets** should be unchanged between two snapshots, assuming no top-ups, withdrawals, seed inserts, or other balance modifications occur between them.

Before test:

```sql
SELECT count(*) AS wallets, sum(balance) AS total_balance FROM wallets;
```

After test, run the same query and compare. For an A↔B-only test, use `WHERE id IN (<A>, <B>)` before and after.

If opening balances were not captured, ledger balance alone cannot reconstruct the expected wallet balances.

## 8. PostgreSQL lock and pool diagnostics

### 8.1 Active sessions and wait events

```sql
SELECT
  pid, state, wait_event_type, wait_event,
  now() - xact_start AS transaction_age,
  now() - query_start AS query_age,
  pg_blocking_pids(pid) AS blocked_by,
  left(query, 180) AS query
FROM pg_stat_activity
WHERE datname = current_database()
  AND pid <> pg_backend_pid()
ORDER BY xact_start NULLS LAST;
```

### 8.2 Blocking chain

```sql
SELECT
  waiting.pid AS waiting_pid,
  blocker.pid AS blocker_pid,
  blocker.state AS blocker_state,
  now() - blocker.xact_start AS blocker_tx_age,
  left(blocker.query, 180) AS blocker_query
FROM pg_stat_activity waiting
JOIN pg_stat_activity blocker
  ON blocker.pid = ANY(pg_blocking_pids(waiting.pid))
WHERE waiting.datname = current_database();
```

`wait_event_type = 'Lock'` means a session is waiting; **it does not by itself establish a deadlock**. A PostgreSQL deadlock typically produces SQLSTATE `40P01` after deadlock detection. An `idle in transaction` blocker or an unexpectedly long transaction deserves investigation.

### 8.3 Database pool metrics

Current application configuration:

```go
sqlDB.SetMaxOpenConns(25)
sqlDB.SetMaxIdleConns(10)
sqlDB.SetConnMaxLifetime(30 * time.Minute)
sqlDB.SetConnMaxIdleTime(5 * time.Minute)
```

Monitor `sqlDB.Stats()`:

```go
stats := sqlDB.Stats()
log.Printf("db open=%d in_use=%d idle=%d waits=%d wait_duration=%s",
    stats.OpenConnections, stats.InUse, stats.Idle,
    stats.WaitCount, stats.WaitDuration)
```

With 100 simultaneous HTTP requests, at most 25 DB connections may be open. Others can wait for a connection; this is normal unless requests fail to make progress.

## 9. Deadlocks, timeouts, and retries

Wallets must always be locked in **ascending wallet ID order**, regardless of transfer direction:

```text
A → B: lock min(A,B), then max(A,B)
B → A: lock min(A,B), then max(A,B)
```

This prevents the common two-wallet lock-order cycle. Other DB objects, triggers, or inconsistent repository access can still introduce deadlocks.

Retry only recognized transient PostgreSQL errors such as:

- `40P01` — deadlock detected.
- `40001` — serialization failure.

Use a bounded number of attempts (currently 3), a short backoff (e.g. 100 ms, 200 ms), and **fresh transfer state for each attempt**. GORM may populate IDs before a rollback; resetting only the database transaction is insufficient.

Optional transaction-scoped lock timeout:

```go
if err := tx.Exec("SET LOCAL lock_timeout = '5s'").Error; err != nil {
    return err
}
```

A lock timeout can surface as SQLSTATE `55P03`; do not assume it is safe or desirable to retry it without an explicit policy. A timeout is an operational safeguard, not a substitute for fixing a blocking transaction. Keep total request deadlines, DB lock timeout, and client timeout aligned.

## 10. Uncertain COMMIT and crash tests

Simulate a connection interruption around `COMMIT` in an isolated test environment. The client may receive an error even though PostgreSQL committed successfully.

Required behavior:

1. Do **not** blindly rerun the transfer after an uncertain commit.
2. Read the idempotency record through a fresh DB transaction/connection.
3. Validate the request fingerprint.
4. If a completed saved response exists, return its original HTTP status/body.
5. If the outcome cannot be confirmed, return an explicit uncertain/unavailable response (e.g. 503) and retain the idempotency key for later reconciliation.

Also test API restart during a request. Any in-memory state must not be relied on for committed transfer correctness; PostgreSQL constraints and transactions are the source of truth.

## 13. Acceptance criteria

The implementation can be considered verified against the assignment's financial correctness requirements when:

- Domain validation tests pass.
- Successful and insufficient-funds integration tests pass.
- Every processed transfer has exactly two correct ledger entries; every failed transfer has none.
- No wallet becomes negative and opening/closing total balances reconcile.
- Concurrent same-sender and opposite-direction tests show no lost updates or permanent stalls.
- Concurrent same-key tests create only one transfer and replay identical status/body.
- Rollback tests prove no partial commits.
- Retry and uncertain-COMMIT tests demonstrate safe outcomes.
- All observed 5xx responses, timeouts, and unexpected PostgreSQL waits are investigated.

```bash
# 1. Run automated tests
go test ./... -count=1

# 2. Start with low concurrency
MODE=opposite COUNT=10 node scripts/concurrency-test.js

# 3. Increase concurrency after checking PostgreSQL

MODE=same-sender COUNT=100 node scripts/concurrency-test.js

# 4. Run the SQL checks from Section 7
# 5. Investigate any failures using Section 8
# 6. Record results in Section 11
```

**Key principle:** A successful HTTP response alone does not prove a safe transfer. Validate the committed database state and concurrency invariants.
