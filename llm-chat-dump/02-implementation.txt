  Decisions I need from you

  1. Slicing: by behavior (above) or by layer (your example)? I recommend by 
     behavior.
  2. Red commits that compile: a missing Go function causes a build error, not a
     test failure. I recommend that Red commits include empty stubs (signatures
     with zero return values). Then they fail on assertions, and every commit
     still builds and lints. The alternative is to treat a build failure as the
     red.
  3. Design gap in §3: the docs ask for three things that can't all hold in Go:
     - the service defines the repository interfaces;
     - the repository doesn't import the service;
     - InTx passes a transaction-scoped repository to fn.

     A method InTx(ctx, func(service.Tx) error) has to name the service's type,
     which forces the import. Options:
     - a. Generic constructor (service.New[*repository.Tx](repo)) that adapts
       the repository's InTx(ctx, func(*Tx) error). The design stays true as
       written, so no doc change. I recommend this.
     - b. Transaction carried in ctx. The signatures are simpler, but the
       transaction is implicit: a wrong ctx silently runs outside it. §3 needs
       rewording.
     - c. Interfaces moved into domain. This mixes persistence ports into the
       domain layer, and §3 changes.
  4. Behavior with no test in §11: logging, the 5 s deadline, server timeouts,
     shutdown, and applying schema and seed at startup. I recommend one red test
     for logging: capture the JSON output and check the fields for a 201 and a
     500, since NFR-5 names those fields. That needs a one-line §11 change in
     its own doc commit. The rest is wiring and lands without a red test. The
     alternative is no logging test either.

  # Wallet Transfer Service

  A Go service on PostgreSQL that moves money between wallets through
  `POST /transfers`. It solves the [assignment](ASSIGNMENT.md):

  - **Idempotency:** every request carries an `idempotencyKey`, stored with
    `UNIQUE` on the transfer; a repeat returns the original response.
  - **Double-entry ledger:** a `PROCESSED` transfer writes one DEBIT and one
    CREDIT entry.
  - **Concurrency:** each transfer runs in one transaction that locks both
    wallets in ID order, so concurrent debits never overspend.
