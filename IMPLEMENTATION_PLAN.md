# Wallet Transfer Service Implementation Plan

## Objective

Build a Go service that implements wallet-to-wallet transfers with idempotent API
semantics, double-entry ledger entries, safe concurrent balance updates, and clear
behavioral tests.

The implementation should stay small enough for the assignment while still showing
the important financial-system decisions: database constraints, transaction
boundaries, row locking, retry safety, and auditability.

## Technical Choices

- Language: Go, using idiomatic `internal/` packages.
- HTTP: standard `net/http` with a small router, or `chi` if dependencies are allowed.
- Database: PostgreSQL as the primary implementation, using `pgx/v5`.
- Amounts: integer minor units only. No floats.
- Currency: default to `USD` when omitted so the service supports the assignment
  payload and the richer design-spec payload.
- IDs: UUIDs generated by PostgreSQL through `gen_random_uuid()`.
- Config: environment variables with sensible local defaults.
- Tests: Go unit tests for domain/service behavior and PostgreSQL integration tests
  for constraints, transactions, and concurrency.

## Consistency Strategy

Use defense in depth:

- Domain and service layers own business meaning: request validation, transfer state
  transitions, idempotency decisions, wallet eligibility, ledger posting intent, and
  failure reasons.
- The database owns concurrent truth: row locks, atomic transactions, uniqueness
  constraints, foreign keys, and balance/amount checks.
- Critical invariants should be expressed in both places where practical. The service
  should prevent invalid operations during normal execution; the database should make
  those invalid states impossible under races, retries, or future code changes.
- Repository methods should expose intent-specific operations, such as
  `LockTransferForProcessing`, `LockWalletsForTransfer`, `InsertLedgerPair`, and
  `CompleteIdempotencyRecord`, so transaction-sensitive behavior is not hidden in
  generic CRUD calls.

## Local Run Workflow

The finished project should be runnable from a fresh checkout with documented commands:

```bash
go mod download
docker compose up -d postgres
make migrate-up
go run ./cmd/server
```

Recommended convenience targets:

```text
make run          # starts the HTTP server
make test         # runs go test ./...
make fmt          # runs gofmt
make fmt-check    # fails if any Go file needs formatting
make lint         # runs golangci-lint
make migrate-up   # applies database migrations
make migrate-down # rolls back the last migration
```

The README should include:

- required tools: Go, Docker, and the migration tool
- environment variables: `PORT` and `DATABASE_URL`
- default local `DATABASE_URL`
- commands to start Postgres, apply migrations, run the server, and run tests
- example `curl` requests for health, wallet reads, transfer creation, transfer reads,
  and ledger reads
- how local seed wallets are created for manual testing

## API Scope

Implement these endpoints:

- `POST /transfers`
- `GET /transfers/{id}`
- `GET /wallets/{id}`
- `GET /wallets/{id}/ledger?cursor=&limit=`
- `GET /healthz`

Request compatibility:

```json
{
  "idempotencyKey": "abc123",
  "fromWalletId": "wallet_1",
  "toWalletId": "wallet_2",
  "amount": 100,
  "currency": "USD"
}
```

`currency` should be optional and default to `USD`.

## Milestone 4: Transfer Execution

Deliverables:

- Implement `TransferService.CreateTransfer`.
- Keep the service workflow explicit and step-oriented:
  - validate request and normalize default currency
  - open or replay idempotency record
  - create or resume `PENDING` transfer
  - lock transfer and wallets
  - evaluate wallet state and funds using domain methods
  - create ledger posting intent using domain constructors
  - persist ledger entries, balances, transfer terminal state, and idempotency snapshot
- Phase 1 transaction:
  - compute request fingerprint from `fromWalletId`, `toWalletId`, `amount`, and
    `currency`
  - insert `idempotency_records` row as `IN_PROGRESS`
  - reject same key with different fingerprint
  - replay same key when completed
  - create `PENDING` transfer for a new key
- Phase 2 transaction:
  - lock transfer row with `FOR UPDATE`
  - return terminal transfers without re-executing or mutating ledger/balances
  - lock both wallets in stable ID order
  - fail terminally for inactive wallets, currency mismatch, or insufficient funds
  - insert one debit and one credit ledger entry
  - update both wallet balances
  - mark transfer `PROCESSED` only through the domain transition method
  - store response snapshot in `idempotency_records`
- Ensure service-level checks are covered by tests, while relying on DB constraints
  as the final guard against concurrent or accidental duplicate writes.

Validation:

- Successful transfer creates exactly two ledger entries.
- Wallet balances update atomically.
- Insufficient funds returns terminal `FAILED` and no ledger entries.
- Inactive wallet and currency mismatch become deterministic failures.
- Terminal transfer replay returns the same response.
- Service tests assert invalid transitions and duplicate processing attempts do not
  call ledger or balance mutation repositories.

## Milestone 5: Transfer API And Error Mapping

Deliverables:

- Add `POST /transfers`.
- Add `GET /transfers/{id}`.
- Map service/domain errors to the contract:
  - `400` for invalid requests
  - `404` for missing wallet or transfer
  - `409` for idempotency key reuse or in-progress replay
  - `422` for inactive wallets
  - `201` for first transfer result
  - `200` for completed idempotent replay
- Return the cached response snapshot for completed duplicate requests.

Validation:

- Handler tests for every response-code row in the spec.
- Contract tests for JSON field names and status codes.

## Milestone 6: Concurrency And Resume Safety

Deliverables:

- Add concurrent transfer tests against the same source wallet.
- Add opposite-direction transfer test: wallet A to B and wallet B to A at the same
  time.
- Add resume path for `IN_PROGRESS` idempotency records with a non-null transfer ID.
- Ensure `processTransfer` is safe to call repeatedly.
- Add tests around the service/DB boundary:
  - service refuses to process a terminal transfer
  - repository update still guards with `WHERE status = 'PENDING'`
  - duplicate ledger insertion is rejected even if the service is called twice

Validation:

- Concurrent debits never make balance negative.
- At most the affordable subset of transfers succeeds.
- No duplicate ledger entries are created under duplicate requests.
- Opposite-direction transfers complete without deadlock.
- Retrying an interrupted `PENDING` transfer completes or returns the terminal result.

## Test Matrix

| Area | Cases |
| --- | --- |
| Validation | missing fields, bad UUID, same wallets, non-positive amount, unsupported currency |
| Happy path | transfer succeeds, balances change, two ledger entries exist |
| Idempotency | same key and same payload replays original result |
| Idempotency conflict | same key and different payload returns `409` |
| In-progress request | concurrent same-key request returns existing terminal result or `409` while racing |
| Failure | insufficient funds becomes terminal `FAILED` |
| Wallet status | frozen or closed wallet fails without posting ledger entries |
| Service guards | terminal transfers cannot be reprocessed; invalid transitions return domain errors |
| Concurrency | simultaneous debits preserve non-negative balance |
| Deadlock avoidance | opposite-direction transfers use stable wallet lock ordering |
| Ledger invariants | each processed transfer has balanced debit and credit totals |

## Key Risks And Decisions

- `currency` differs between the assignment and design spec. Treat it as optional and
  default to `USD`.
- Wallet creation is not in the core assignment. Use seed data or test fixtures unless
  a small development-only create endpoint is explicitly needed.
- PostgreSQL row locking is the clearest concurrency strategy for the assignment.
  Optimistic locking can stay out of the first implementation.
- Service-level guards are still required for readability, testability, and correct
  business semantics. They should not be treated as the concurrency boundary; database
  locks and constraints remain the final authority under races.
- Failed validation such as malformed payloads and missing wallets should not create a
  transfer row. Insufficient funds should create a terminal `FAILED` transfer because
  it is an auditable attempted financial movement.
- Idempotency should rely on database uniqueness and cached response snapshots, not
  only service-level checks.
