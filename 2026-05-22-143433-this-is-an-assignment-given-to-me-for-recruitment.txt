❯ Before starting, explain to me in detail how these money transfer systems     
  work in Banks. Are they 100% safe from failures?. If no then how do we handle 
   these systems?                                                               

● Good question. Directly maps to assignment. Explain real bank systems, then
  tie back.

  Core idea: money never "moves", it's recorded

  Banks don't teleport value. They record entries in ledgers. Money "transfer" =
   debit one account, credit another. Truth = the ledger, not a balance field.
  Balance = sum of ledger entries.

  Double-entry bookkeeping (500+ yr old, still foundation):
  - Every transaction = ≥2 entries. Total debits == total credits. Always.
  - Invariant: sum of all entries across system == 0 (closed system) or ==
  external settlement.
  - Why: makes errors detectable. Unbalanced ledger = bug/fraud, caught by
  reconciliation.

  This is exactly the assignment's double-entry ledger requirement.

  Layers of a transfer

  Intra-bank (both accounts same bank): one DB transaction, debit + credit
  atomic. Easy case. ACID handles it.

  Inter-bank (different banks): no shared database. Bank A can't write to Bank
  B's ledger. Solved by:
  - Settlement through a common third party — central bank. Both banks hold
  accounts at central bank. Real movement happens there.
  - Systems: RTGS (real-time gross settlement, per-transaction, large value),
  NEFT/ACH (batched netting), SWIFT (messaging only — tells banks what to do,
  doesn't move money), UPI/card networks (switch routes + settles later).
  - Key: messaging layer ≠ settlement layer. Message says "pay X". Actual
  settlement nets later. Gap between them = risk window.

  ACID — the local guarantee

  Single-DB transfer relies on:
  - Atomicity: debit + credit both happen or neither. No half-transfer.
  - Consistency: invariants hold (no negative balance, ledger balances).
  - Isolation: concurrent transfers don't corrupt each other (your concurrency
  requirement).
  - Durability: committed = survives crash (write-ahead log / WAL on disk).

  ACID solves the single-database problem. Bank-to-bank ACID across two systems
  = impossible (no global transaction). That's where it gets hard.

  Are they 100% safe? No.

  Nothing distributed is 100% safe. Hard limits:

  CAP theorem: under network partition, choose Consistency OR Availability.
  Can't have both. Banks usually pick consistency for money (refuse rather than
  risk wrong balance).

  Two Generals / FLP: can't guarantee two separate systems agree perfectly over
  an unreliable network. There's always a window where A thinks "done", B thinks
   "not yet".

  Real failure modes:
  - Duplicate message (network retry) → double charge
  - Lost response → client retries → double charge
  - Crash mid-transfer → partial state (money left A, never reached B)
  - Two debits race → double spend / negative balance
  - Clock skew, message reordering

  So safety ≠ "no failures." Safety = failures don't corrupt the ledger, and
  every failure is detectable + recoverable.

  How banks handle failure (the real techniques)

  1. Idempotency keys
  Every request carries unique ID. Retry with same key → system returns original
   result, no second effect. Exactly your idempotencyKey requirement. This is
  THE defense against duplicate/retry. Used everywhere — Stripe, card networks,
  UPI.

  2. State machine + guarded transitions
  Transfer isn't boolean done/not-done. Lifecycle: PENDING → PROCESSED | FAILED.
   Each transition guarded so a retry can't move it twice. Lets you safely
  resume after crash: look at state, continue from there.

  3. Two-phase commit (2PC)
  Coordinator asks all parties "can you commit?" (prepare). Only if all say yes
  → "commit". Gives atomicity across systems. Cost: blocking — if coordinator
  dies after prepare, parties locked. Slow. Banks use it internally but it
  doesn't scale well + has the coordinator-failure hole.

  4. Sagas (compensating transactions)
  Modern distributed answer. Break transfer into local steps, each with an
  "undo". If step 3 fails, run compensations for 1–2. Example: reserve funds →
  if downstream fails → release reservation. Money is eventually consistent, not
   instantly. Most fintech runs this.

  5. Reservation / hold pattern
  Don't debit instantly. Place a hold (authorization) → confirm later (capture)
  → or expire. Card "pending" charges = this. Decouples promise from settlement.

  6. Reconciliation
  The safety net. Periodically (often daily) compare your ledger vs
  counterparty's vs central bank's. Mismatches flagged, investigated, corrected
  with adjusting entries. Assumes failures WILL slip through and catches them
  after the fact. Banks trust reconciliation more than real-time perfection.

  7. Write-ahead log + durability
  Commit = first write intent to disk log, then apply. Crash → replay log on
  restart. No committed transfer lost.

  8. Outbox pattern
  To reliably tell other systems without losing messages: write the event to an
  outbox table in the same DB transaction as the ledger change. Separate process
   reads outbox, publishes. Guarantees "if ledger changed, message will
  eventually send" — no lost-message gap.

  Mental model

  Prevent          Detect           Recover
  -------          ------           -------
  idempotency      reconciliation   sagas/compensation
  ACID tx          invariant checks WAL replay
  row locks        ledger balance   adjusting entries
  2PC/saga         audit            manual ops desk

  Banks layer all three. Real systems also have a human ops/disputes desk for
  the residual that automation can't fix. That's the honest answer: not 100%
  automated-safe — designed so the unsafe slice is small, detectable, and
  reversible.

  Tie back to your assignment

  Scaled-down version of all this. You'll implement:
  - Double-entry ledger → the truth source
  - ACID transaction → atomic debit+credit (single DB, so no 2PC/saga needed —
  say this in PR)
  - Idempotency key → duplicate/retry defense
  - Row locks → concurrency safety, no double-spend
  - State machine → safe transitions under retry

  What you'll deliberately skip (and mention as out-of-scope tradeoff in PR,
  shows senior thinking):
  - 2PC / sagas — single DB, not needed
  - Reconciliation jobs — overkill for assignment
  - Inter-bank settlement — not in scope

  Naming these as conscious exclusions = the "good engineering decisions" they
  grade.

● Good — security is graded too (SonarQube + secret scanning configured in this
  repo). Here precautions, then tie to assignment.

  1. Language / runtime choice

  - Memory safety first. Avoid C/C++ for new services — buffer overflows,
  use-after-free = top exploit class. Prefer Go, Rust, Java, C#. Go (your
  assignment lang) is memory-safe + GC, no manual pointer arithmetic.
  - Mature stdlib for crypto/TLS. Don't hand-roll. Go crypto/tls, Java JCE —
  audited, FIPS-validated options exist.
  - Strong typing + static analysis friendly. Catches bugs at compile, not
  runtime in prod.
  - Boring > new. Banks pick proven tech (Java, Go, Postgres, Oracle), not
  bleeding-edge. Long support, large security-patch history, big talent pool.

  2. Dependencies / supply chain

  Biggest modern attack surface. Precautions:
  - Minimal deps. Every library = attack surface + transitive risk. Go culture
  (small deps) helps.
  - Pin versions + lockfile (go.sum). Reproducible builds, no silent upgrade to
  malicious version.
  - SCA scanning — Software Composition Analysis. govulncheck, Dependabot, Snyk.
   Flags known CVEs in deps.
  - Vendoring / private proxy — internal module mirror, not pulling straight
  from public internet at build.
  - SBOM (Software Bill of Materials) — track every component for audit/CVE
  response.
  - Verify checksums + signatures. Defends against compromised registry (the
  npm/xz-style attacks).

  3. Database

  - ACID engine, no compromise. Postgres, Oracle, DB2. Money needs durability +
  isolation guarantees.
  - Parameterized queries only — never string-concat SQL. Kills SQL injection
  (OWASP #3). ORMs/query builders enforce this.
  - Least-privilege DB users. App account can't DROP tables or read other
  schemas. Separate read/write roles.
  - Encryption at rest + in transit. TDE (transparent data encryption) + TLS to
  DB.
  - Constraints enforce invariants — DB-level CHECK, FK, UNIQUE. Don't trust app
   code alone (your evaluation_guide literally asks: "does code rely on app
  logic where DB should enforce?").

  4. Secrets management

  - No secrets in code/repo. Ever. (This repo has secret-scanning in checklist
  for exactly this.)
  - Vault / KMS — HashiCorp Vault, AWS KMS, cloud secret managers. Rotate keys.
  - Short-lived credentials over long-lived static keys.
  - Env injection at runtime, not baked into image.

  5. Transport + API security

  - TLS everywhere, mutual TLS (mTLS) service-to-service. No plaintext internal
  traffic.
  - AuthN + AuthZ — OAuth2/OIDC, mTLS, signed requests. Verify identity AND
  permission per call.
  - Input validation at boundary — reject malformed before it hits business
  logic.
  - Rate limiting + idempotency — prevent abuse, replay. (Idempotency = security
   control too, not just correctness.)

  6. Build / deploy pipeline

  - SAST — Static Application Security Testing. SonarQube (configured in this
  repo!), CodeQL. Scans source for vuln patterns.
  - DAST — runtime/penetration scanning against deployed app.
  - Signed artifacts + immutable images. Container image scanning (Trivy,
  Grace).
  - Reproducible, hermetic builds. Same input → same binary. Detects tampering.
  - 4-eyes / branch protection — required reviews, no direct push to main (this
  repo's branch-protection-checklist = exactly this). Code review is a security
  control.

  7. Runtime hardening

  - Least privilege — non-root containers, dropped Linux capabilities, read-only
   filesystem.
  - Network segmentation — app can only reach DB it needs. Firewall/security
  groups.
  - Audit logging — every money operation logged immutably. Tamper-evident.
  - Observability — detect anomalies (spike in failed transfers = attack
  signal).

  8. Compliance frameworks (force the above)

  - PCI-DSS (cards), SOC 2, ISO 27001, regional (RBI in India, PSD2 in EU).
  - These aren't bureaucracy — they codify the checklist: encryption, access
  control, audit, patching SLAs, segregation of duties.

  No single control trusted. Layer them. Assume each layer can fail:
  Network → TLS/mTLS → AuthN/Z → input validation →
  parameterized queries → least-priv DB → DB constraints →
  encryption at rest → audit log → monitoring
  Breach one, others still hold.

❯ What about ORMs? What if ORM is compromised or there a bug in ORM that        
  transactions does not work as properly?                                       

● Sharp question. Gets at trust boundaries. Two separate risks: ORM compromised
  (supply chain) vs ORM buggy (correctness). Different defenses.

  Risk A: ORM has a bug — transactions don't work right

  Real, documented. Examples of how ORMs silently break transaction safety:

  - Silent connection swap. ORM connection pool hands different physical
  connections mid-"transaction" → your BEGIN and your UPDATE run on different
  connections → no actual transaction. Classic in mismanaged pools.
  - Autocommit leak. ORM thinks it's in a transaction, driver actually
  autocommits each statement. Each write commits alone. Crash mid-way = partial
  transfer.
  - Lazy loading outside tx. ORM defers a query; it fires after transaction
  closed → reads inconsistent data.
  - Isolation level not honored. You ask SERIALIZABLE, ORM/driver default
  overrides to READ COMMITTED. Race window opens silently.
  - Nested transaction faking. Many ORMs fake nested tx with savepoints. Inner
  "rollback" doesn't roll back what you think.
  - Lock lost. SELECT ... FOR UPDATE through ORM abstraction sometimes drops the
   lock clause, or runs in a separate session = no lock.

  For money, these are catastrophic AND silent — no error, just wrong balance
  found later.

  Risk B: ORM compromised (supply chain)

  Malicious code injected into the library (registry hack, maintainer account
  stolen, dependency confusion). ORM sees every query + credentials → can
  exfiltrate data, alter writes, skim funds. ORMs are deep deps with broad
  access = high-value target.

  How banks/serious fintech handle it

  1. Many don't use full ORMs for money paths.
  Core ledger code often uses raw SQL or thin query builders, not heavy ORM.
  Reasons:
  - Transaction + lock behavior is explicit and visible, not hidden behind
  abstraction.
  - You see exactly what SQL hits the DB.
  - Fewer layers = fewer places for silent bugs.
  - ORM fine for CRUD/admin screens; money ledger gets raw SQL.

  This is why for your assignment I recommend pgx (raw-ish) over GORM. You
  control BEGIN/COMMIT/FOR UPDATE explicitly. Easy to justify in interview: "I
  kept transaction boundaries explicit so locking behavior is auditable, not
  hidden by an ORM."

  2. Don't trust app/ORM for correctness — push invariants to DB.
  This is the key principle. Even if ORM mangles a transaction, the database 
  constraints still hold the line:
  - CHECK (balance >= 0) → DB rejects overdraft even if app logic raced.
  - UNIQUE (idempotency_key) → DB rejects duplicate even if ORM dedup failed.
  - Double-entry sum check / triggers → unbalanced ledger rejected.
  - FK constraints → no orphan ledger row.

  DB is the last line. ORM bug can't violate a DB constraint. Your
  evaluation_guide asks this exact thing: "Does code rely on application logic 
  where the database should enforce correctness?"

  3. Verify, don't assume.
  - Integration tests against real DB — not mocks. Test that a concurrent
  double-debit actually fails. If ORM drops the lock, the test catches it.
  Behavioral test = ORM-bug detector.
  - Test rollback actually rolls back. Force a mid-transaction failure, assert
  no partial state.
  - These tests are exactly what the assignment asks for (concurrency + failure
  tests).

  4. Supply-chain defenses (same as before, applied to ORM):
  - Pin version + checksum (go.sum), SCA scan (govulncheck), SBOM.
  - Prefer widely-used, audited libs — bigger eyeballs, faster CVE response.
  - Minimal deps — fewer ORMs/plugins = smaller target.

  5. Reconciliation catches the residual.
  If ORM bug slips past tests + constraints, daily ledger reconciliation finds
  the imbalance. Defense in depth again: prevent (raw SQL) → constrain (DB) →
  detect (recon).

  The meta-principle

  Never let a library be the only thing standing between you and a wrong 
  balance.

  ORM/app logic   ← convenient, fast to write, CAN silently break
       ↓ but backed by
  DB constraints  ← enforce truth regardless of app bug
       ↓ verified by
  integration tests ← prove behavior on real DB
       ↓ and caught by
  reconciliation  ← detect what slipped through

  Trust is layered, not placed in one component.

  First: not all same layer.

  So sqlc ≠ alternative to pgx — sqlc sits on top of pgx. Real choice = how much

● Transactions — quick recap

  Transaction = group of operations that succeed together or fail together. DB
  either applies ALL or NONE. WAL (write-ahead log) enables crash recovery.

  Key for transfers: debit + credit + ledger entries + idempotency record → one
  transaction. Partial success = corrupted ledger.

  ---
  Lock Types (Postgres)

  1. Shared Lock (S) — SELECT ... FOR SHARE

  - Multiple readers can hold simultaneously.
  - Blocks writers, not other readers.
  - Use: "I'm reading this row, prevent deletion but allow concurrent reads."

  2. Exclusive Lock (X) — SELECT ... FOR UPDATE

  - Only ONE holder at a time.
  - Blocks all other readers-with-locks + writers.
  - Use: "I'm about to modify this row, no one else touches it."

  3. Table-Level Lock — LOCK TABLE wallets

  - Locks entire table.
  - Overkill for row operations. Kills concurrency.
  - Avoid for transfers.

  4. Advisory Locks — pg_advisory_xact_lock(id)

  - App-controlled, not tied to specific row/table.
  - Must manually acquire/release.
  - Use: custom serialization logic outside row model.

  5. Optimistic Locking (no real DB lock)

  - Add version column. Read version, write only if unchanged (WHERE id = X AND 
  version = N).
  - No lock held between read and write.
  - Retry on conflict (CAS — compare and swap).

  ---
  Transaction Isolation Levels (Postgres)

  Four levels, each preventing different anomalies:

  ┌───────────────┬─────────────────┬─────────────────┬────────────┬────────┐
  │     Level     │   Dirty Read    │ Non-Repeatable  │  Phantom   │  Cost  │
  │               │                 │      Read       │    Read    │        │
  ├───────────────┼─────────────────┼─────────────────┼────────────┼────────┤
  │ READ          │ possible        │                 │            │        │
  │ UNCOMMITTED   │ (Postgres       │ possible        │ possible   │ lowest │
  │               │ treats as RC)   │                 │            │        │
  ├───────────────┼─────────────────┼─────────────────┼────────────┼────────┤
  │ READ          │ prevented       │ possible        │ possible   │ low    │
  │ COMMITTED     │                 │                 │            │        │
  ├───────────────┼─────────────────┼─────────────────┼────────────┼────────┤
  │ REPEATABLE    │ prevented       │ prevented       │ prevented* │ medium │
  │ READ          │                 │                 │            │        │
  ├───────────────┼─────────────────┼─────────────────┼────────────┼────────┤
  │ SERIALIZABLE  │ prevented       │ prevented       │ prevented  │ high   │
  └───────────────┴─────────────────┴─────────────────┴────────────┴────────┘

  *Postgres REPEATABLE READ also prevents phantoms (better than SQL standard).

  What each anomaly means for transfers:

  Dirty Read — read uncommitted data from another tx. Never want this. Postgres
  never does this anyway (min = READ COMMITTED effectively).

  Non-Repeatable Read — read balance twice in same tx, get different value
  because another tx committed between reads. Dangerous for: read balance →
  validate → update balance. Balance changed between read and update = race.

  Phantom Read — query for rows matching condition, re-query same condition, get
   different rows. Relevant for ledger sum queries.

  ---
  What this assignment needs — and WHY

  The race condition to defeat:

  Tx A: SELECT balance FROM wallets WHERE id = 'wallet_1'  → 100
  Tx B: SELECT balance FROM wallets WHERE id = 'wallet_1'  → 100
  Tx A: debit 80  → UPDATE balance = 20  ✓
  Tx B: debit 80  → UPDATE balance = 20  ✓  ← WRONG. Should have failed. Double
  spend.

  This is a read-then-write race. Both read 100, both think 80 is valid, both
  write 20. Balance should be -60 but DB shows 20. Lost update problem.

  Solution: SELECT ... FOR UPDATE (pessimistic row lock)

  BEGIN;
  SELECT balance FROM wallets WHERE id = 'wallet_1' FOR UPDATE;
  -- Tx B now BLOCKS here, waiting for Tx A to finish
  -- Tx A validates balance, does debit
  UPDATE wallets SET balance = balance - 80 WHERE id = 'wallet_1';
  COMMIT;
  -- Tx B unblocks, re-reads balance = 20, validation fails correctly

  Why pessimistic over optimistic here:
  - High contention expected on hot wallets (same wallet debited repeatedly).
  - Optimistic = read → write → fail → retry loop. Under high contention, many
  retries, more load.
  - Pessimistic = one waits, one proceeds. Simpler code path, no retry logic
  needed.
  - For assignment: fewer moving parts = clearer correctness story.

  Isolation level: READ COMMITTED (Postgres default)

  Might seem counterintuitive. Why not SERIALIZABLE?

  Because FOR UPDATE already gives you the guarantee you need at row level —
  stronger than READ COMMITTED normally provides, without the overhead/abort
  rate of SERIALIZABLE.

  With FOR UPDATE:
  - Lock held from SELECT to COMMIT.
  - Concurrent tx on same wallet BLOCKS until first commits.
  - After first commits, second reads updated balance (READ COMMITTED sees
  latest committed value).
  - Race eliminated at the wallet row level.

  SERIALIZABLE adds full transaction-level conflict detection. Would abort more
  transactions unnecessarily. Higher retry rate, more complexity, for no
  correctness gain when you've already locked the specific rows.

  Exception: if you were using complex range queries or ledger sum validation
  inside the transaction, SERIALIZABLE or REPEATABLE READ would protect against
  phantoms. For single-wallet balance check + update, READ COMMITTED + FOR
  UPDATE is sufficient and conventional.

  Deadlock prevention: deterministic lock ordering

  Two concurrent transfers involving same two wallets can deadlock:

  Tx A locks wallet_1 → waits for wallet_2
  Tx B locks wallet_2 → waits for wallet_1
  ← deadlock

  Fix: always lock wallets in consistent order (e.g., lower UUID first):

  // Lock wallet with smaller ID first, always
  if fromWalletID < toWalletID {
      lockWallet(fromWalletID)
      lockWallet(toWalletID)
  } else {
      lockWallet(toWalletID)
      lockWallet(fromWalletID)
  }

  Postgres detects deadlocks and kills one tx (returns error), but better to
  prevent entirely.

  ---
  Decision summary

  ┌─────────────────────────────┬───────────────────────────────────────────┐
  │           Choice            │                  Reason                   │
  ├─────────────────────────────┼───────────────────────────────────────────┤
  │ SELECT ... FOR UPDATE on    │ Exclusive row lock, blocks concurrent     │
  │ both wallets                │ debit on same wallet                      │
  ├─────────────────────────────┼───────────────────────────────────────────┤
  │ READ COMMITTED isolation    │ Sufficient with FOR UPDATE, less overhead │
  │                             │  than SERIALIZABLE                        │
  ├─────────────────────────────┼───────────────────────────────────────────┤
  │ Deterministic lock order    │ Prevents deadlock on two-wallet transfers │
  ├─────────────────────────────┼───────────────────────────────────────────┤
  │ Pessimistic over optimistic │ Lower code complexity, better for         │
  │                             │ hot-wallet contention                     │
  ├─────────────────────────────┼───────────────────────────────────────────┤
  │ DB constraints as backup    │ CHECK balance >= 0 catches anything that  │
  │                             │ slips past app logic                      │
  └─────────────────────────────┴───────────────────────────────────────────┘

● Stored Balance vs Derived Balance — correctness lens

  1. Stored Balance (wallets.balance column, updated each transfer)

  Pros (correctness):
  - DB enforces invariant directly. CHECK (balance >= 0) rejects overdraft
  atomically. Single source, single guard.
  - Atomic check+update in one row. UPDATE ... SET balance = balance - amount 
  WHERE balance >= amount — the read, validate, write happen as one locked
  operation. No window.
  - FOR UPDATE locks one row. Clear, cheap concurrency boundary. Lock the wallet
   row, done.
  - No aggregation drift risk at read — balance is one value, can't be
  miscomputed by a wrong query.

  Cons (correctness):
  - Two sources of truth — balance column AND ledger entries. They can diverge
  if a bug updates one but not the other. Ledger says X, balance says Y.
  - Requires discipline: every balance mutation MUST happen in same transaction
  as ledger insert, or they desync.
  - No built-in audit cross-check unless you reconcile balance vs ledger sum
  periodically.
  - Bug in update logic → wrong balance persists silently until someone
  reconciles.

  2. Derived Balance (sum ledger entries on read)

  SELECT SUM(CASE WHEN type='CREDIT' THEN amount ELSE -amount END)
  FROM ledger_entries WHERE wallet_id = ?

  Pros (correctness):
  - Single source of truth = the ledger. Balance is always exactly what entries
  say. Cannot diverge — it's computed, not stored.
  - Ledger is append-only — immutable facts. No update = no update bug.
  Strongest audit story.
  - Self-consistent by construction. No reconciliation needed; the sum IS the
  truth.
  - Matches how real accounting/banks think — balance is a view over the
  journal.

  Cons (correctness):
  - Overdraft check is harder to make atomic. To validate "enough funds" you
  must: sum ledger → compare → insert debit entry. That read-then-write spans
  rows, not one row. Race window unless you lock.
  - What do you lock? No single balance row to FOR UPDATE. Options:
    - Lock the wallet row anyway (keep wallets row as a lock anchor, even
  without balance column).
    - SELECT ... FOR UPDATE on ledger rows — locks existing rows but NOT future
  inserts → phantom read. New concurrent insert slips in. Need SERIALIZABLE or
  advisory lock.
  - Cannot put CHECK (balance >= 0) on a computed value. No simple DB-level
  overdraft guard. Enforcement moves to app + isolation level → exactly what
  evaluation_guide warns against ("relying on app logic where DB should
  enforce").
  - Performance: every read sums full history. Grows unbounded. Needs
  snapshot/checkpoint rows at scale (added complexity).
