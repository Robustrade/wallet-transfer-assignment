## My Current Design

This is my initial thought process.

### Request Flow

1. Validate the source wallet exists.
2. Verify the source wallet has sufficient balance.
3. Validate the destination wallet exists.
4. Check whether the supplied idempotency key has already been processed.
5. If validation succeeds, continue with transfer execution.

### Transaction Flow

Inside a single database transaction:

1. Create a Transfer record with status `PENDING`.
2. Create debit and credit ledger entries.
3. Update both wallet balances.
4. Mark the transfer as `COMPLETED`.
5. Commit the transaction.

### Failure Handling

If any operation fails:

- Rollback the transaction.
- If the failure is caused by row-level lock contention or serialization conflicts, retry using exponential backoff.
- Limit retries to avoid infinite retry loops.
- If retries are exhausted:
  - Either rollback everything completely (preferred if possible), or
  - If partial persistence is intentionally required, clearly justify why and describe the recovery mechanism.
- Explain the tradeoffs between these approaches.

### Idempotency

Current idea:

- Store the idempotency key in the `transfers` table with a unique constraint.
- Add Redis as a fast middleware cache with a TTL of 24 hours to reject obvious duplicate requests before they reach the business layer.
- Explain whether Redis is actually beneficial here or whether PostgreSQL alone is sufficient.
- Consider race conditions between Redis and PostgreSQL.
